# Browser enrollment store

## Small production boundary

Add an explicit IndexedDB adapter for independently approved enrollment material: public configuration plus existing non-exportable TLS, grant and relay P-256 signing keys. It stores browser-native CryptoKey objects, never private-key JSON, presenter callbacks or an `approved: true` import. The trusted operator supplies the material only through `installApproved(expectedRevision, load, signal)`; the loader receives only the original signal, never a candidate or selector. This API is not an identity-authentication ceremony. The owner must already have independently authorized persistence and bound the public identities to the supplied handles.

Origin-isolated browser storage and controlled same-origin code are the trust boundary. This does not protect against malicious same-origin scripts, privileged browser/OS access, disk rollback, eviction, backups or copied browser profiles. Storage loss is Locked, not permission to recreate credentials. The normal product now supplies a lazy fixed-database reader, but no default enrollment action or independent registration provider. See [product startup](browser-product-provider.md).

## Record and ownership

One fixed record per explicitly selected database has a canonical positive u64 revision. An active v1 record contains the configuration and three original key handles. `revoking` and `revoked` tombstones contain no keys. Installation accepts only an empty store or an exact explicitly supplied revision of a completed revoked record; active/revoking records cannot be replaced. Explicit replacement advances the revision. All mutations wait for the original transaction `complete`, not request `success`, and use the strict durability hint. The hint is not a guarantee against disk rollback or browser eviction.

`openExisting(present, signal)` acquires the browser's origin-scoped exclusive Web Lock with `ifAvailable`; competing pages remain unavailable rather than queueing an automatic later activation. It subscribes before reading, validates the stored record, creates one existing page-local enrollment authority, and supplies original loaded keys plus newly bound controlled callbacks. The existing candidate helper still compares every field before connection. The lock remains owned through the authority's original complete retirement. Unknown retirement keeps the lock held and rejects the caller's completion; it is not turned into successful cleanup.

`revoke()` first atomically writes a key-free `revoking` tombstone. New reads and replacements are blocked immediately. BroadcastChannel is only a cancellation hint, not proof of retirement. Each activation first commits a random public owner marker. Only that original owner, after its actual `waitClosed()` succeeds, may atomically clear its exact revision/marker. Final `revoked` requires both the original exclusive ownership to be released and the durable marker to be absent. A missing notification, an ignored abort or a suspended live owner can leave revocation pending. There is no forced lock steal, timeout-as-success, fallback store, or automatic retry. If a revocation is interrupted, the durable `revoking` record stays locked and a later explicit revoke can finish it only if the original owner completion was committed. Browser context destruction releases its native lock but leaves an uncleared marker permanently fail-closed; it is not retirement proof or permission to clear the marker. Recovery from that state is deliberately not implemented.

## Isolated implementation plan

1. Actual Edge tests first: store missing is Locked; explicit synthetic install survives a new page; all loaded keys stay non-exportable; competing activation is unavailable; readonly metadata omits handles.
2. Implement strict record snapshots and original IndexedDB transaction completion, then explicit install and one-shot page activation into the existing authority.
3. Add revocation races: pending original retirement, late load, revocation interrupted by tab exit, stale revision replacement, duplicate revoke, and failed/aborted installation. No cancelled transaction may appear committed merely because a request succeeded.
4. Connect an explicitly installed TEST_ONLY record to the original full Browser/Relay/Host/WASM fixture: install in one page, close it, load in a fresh page, approve the real production presenter, observe one exact memory-writer effect, revoke, and prove another page remains Locked before signing/connecting.
5. Run strict module typechecks, existing supplier/authority and remote package tests, final actual Edge acceptance and independent review; commit only this slice.

The test browser uses a project-contained temporary profile and fixed published TEST_ONLY key scalars. No user key, real WebAuthn registration, credential configuration, native GUI approval, deployment or external transmission is performed. A real operator workflow must obtain explicit permission for the specified credential storage and destination before invoking installation.

The browser primitives' completion semantics follow [IndexedDB](https://www.w3.org/TR/IndexedDB/) and [Web Locks](https://www.w3.org/TR/web-locks/). The existing [page-local authority](browser-enrollment-lifecycle.md) and [grant presenter](browser-grant-presentation.md) retain their separate duties.

## Controlled module and actual permission boundary

`createStoredBrowserProfileReader(candidateBytes, store, present)` composes one original store admission with the existing strict pairing helper. It caches success, missing and failure, never reloads storage or silently constructs a replacement authority. Every cached return checks the current signal, original signal and enrollment signal. Initialization comparison failure closes and waits for the original session; a general read rejection is not a retirement receipt. An original open failure or later caller cancellation can reject while the underlying lock/owner is still correctly retained. Only the session's `waitClosed()` establishes that scoped completion.

The module served as `/browser-profile.js` still exports only `readApprovedBrowserInputs`. Keep install/revoke controls in separately authorized owner code, not in that export. New Host run/generation data requires independently approved replacement material after completed revocation; it is not edited into an active stored record. The database name is explicitly selected by trusted code and is never taken from the public candidate.

Before any real installation, obtain explicit authorization for the actual HTTPS origin, selected existing TLS/grant/relay handles, public Host/browser binding, persistent local storage and later per-grant use. This code does not create a WebAuthn credential, authenticate an operator, discover keys, or prove the initial public/private binding. Native Host approval and the original WebAuthn grant approval remain required. Revocation removes the stored key handles; if no verified recoverable copy exists, that may be irreversible and needs the applicable destructive-action confirmation. None of these real actions was performed by the synthetic tests.

Acceptance uses the actual product page and production persisted reader/presenter. A separate TEST_ONLY installer commits independent Host-derived metadata and existing fixed keys; a new page loads the structured-cloned handles without reimporting TLS/grant/relay private material. Only the synthetic authenticator imports its public fixture scalar when the grant requests WebAuthn. Cross-page revoke closes the active original chain, commits the tombstone, and another page stays Locked with zero signing, key imports or Relay connections. A changed candidate is also refused without modifying the independent stored approval.

Actual IndexedDB and Web Lock races are in `tests/remote-browser/browser-enrollment-store.spec.ts`; full-chain cases are `PersistedSupplier` and `PersistedRecord` in `browser-entry.spec.ts`. Set all runtime temporary directories inside the project as in the existing acceptance commands.
