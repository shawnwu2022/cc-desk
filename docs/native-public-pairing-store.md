# Native public pairing store

This opt-in Windows `remote-host` component stores public device configuration only. Loading returns a `LockedSnapshot`, with no conversion into a run owner, active supplier, Host approval, grant or connection. It performs no native key operation or network operation. Missing is not initialization. Corruption is not repaired, and staged files are never fallback data.

The versioned, domain-separated document contains a nonzero canonical store UUID, monotonically checked revision and at most 32 active or revoked device entries. Active records contain stable native profile/key names and SPKIs, verified browser credential/public-key/backup metadata, public relay route and principal. Unknown and duplicate JSON fields, duplicate device IDs, invalid states/identities/origins/keys, revision overflow and bounded-file violations are rejected. No run/session/generation/scope/activation/incarnation/approval/permit/owner/Instant/private key is persisted. Forget creates an identity-only tombstone for future suggestions; it does not revoke an independently approved live connection.

Production sealing uses current-user DPAPI on the entire bounded envelope, including a SHA-256 digest of its canonical document, with fixed domain entropy and `CRYPTPROTECT_UI_FORBIDDEN`. It never sets `CRYPTPROTECT_LOCAL_MACHINE`. DPAPI is not application-exclusive, proof of the original GUI Yes, hardware/user identity verification, or protection against rollback to an old valid blob. A valid old blob can reintroduce an old public suggestion, but it remains Locked and needs fresh admission and approval.

The adapter uses a separate `remote-pairings-v1` directory under an explicitly supplied existing local NTFS parent. It reuses current-user-only descriptor verification, handle-relative no-reparse traversal, pinned parent/file identities, single-link checks and permanent cross-process lease files. It does not reuse the history store directory or weaken its sharing/replacement policy. Reads take the same control lock. Writes perform store-ID/revision/state CAS, create a private same-directory stage, write and sync it, then recheck the exact native approval immediately before the publication syscall. Initial rename performs its final check after all path/identity checks and the test probe; replacement rechecks after releasing the old and staged file handles. Existing active devices cannot be overwritten by Remember.

Replacement uses strict `ReplaceFileW` flags zero, with no ignore-ACL flag or fallback rename. Target and stage handles are released only while the original private parent and control lock remain held. The replacement is reopened, checked for exact staged identity and bytes, and synced. Initial publication uses no-replace handle-relative rename. Every failure after publication is attempted is Unknown and poisons that store instance; it never retries the previous approval. Reopening only reconciles public Locked state. Orphan stage files are retained and never interpreted as committed state.

The separate native approval gate must consume a one-shot, exact-target/exact-mutation permission, bound to the original verified evidence, document/run and deadline. The internal authorization trait is not a JavaScript DTO or a persistence approval constructor. `StoreTarget` binds approval to the original store object and its verified private directory label. Creating a directory is an explicit setup step, not implicit load or durable approval.

`NativePersistenceApproval` retains the original `UnapprovedBrowserRegistration` and frozen native supplier metadata. It renders the exact record and target under a separate native dialog purpose; a run-local, browser-storage or Host-session Yes cannot substitute for it. The registration session moves the same evidence into this gate, consumes it once for the store operation, and returns that original evidence only on a definite successful commit so the separate browser-storage gate can continue. A failed or uncertain store attempt closes this registration stage; it cannot replay the old Yes. Unknown and ordinary failure are distinct safe errors, and a late cancellation does not erase a completed historical write.

This component is not yet a production Remember/Forget command or startup hydration path. The first-registration product entry remains separate. Even after product wiring, loading a remembered record cannot repair the browser's old run scope: a fresh authenticated scope handoff and fresh Host approval remain necessary. The isolated registration oracle composes this gate with a synthetic sealer, reopens the file as Locked, then continues through the original browser-storage approval; it does not establish native restart remote control.

Tests are synthetic-only: DPAPI is hard-disabled in test builds; public P-256 points are constants, not created/opened keys. Files and child TEMP/TMP live under the checkout `.audit`. The test matrix covers reload/tombstones, target mismatch and expiry after staging, strict decode and bounds, corruption, overflow, competing actual subprocess CAS, core Unknown poisoning, real replacement followed by an injected Unknown, hardlink rejection, and deterministic revocation at the initial rename syscall boundary. These tests do not constitute actual user DPAPI, real named-key, GUI dialog, phone or public-network acceptance. Execution results must be recorded from the current compiled artifact, not inferred from these test definitions.
