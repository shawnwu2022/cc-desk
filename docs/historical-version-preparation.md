# 历史版本：目录与安装包准备

设置 → 更新 → 官方历史版本可读取官方 `shawnwu2022/cc-desk` 发行目录，显示当前平台的可用性，并明确选择一个版本。每页至多 25 条，最多读取 10 页；达到上限会显示列表可能不完整。筛选只作用于已加载的版本。草稿、测试产物和候选包不进入官方历史目录。

选择后可执行“下载并验证安装包”。Rust 持有官方发行版、安装包与签名的元数据，前端不提供下载 URL、安装路径或文件内容。后端重新检查元数据，只接受受限的官方 GitHub 资产跳转，并在私有目录验证发布者 Minisign 签名、SHA256 与大小。发布者验证成功不等于安装包身份或安装准入已通过。Windows x64 普通构建在匹配已审核的完整 payload 后提供安装确认；实际切换仍须重新通过源安装、会话、进程和返回点检查。自动客户端更新策略与历史版本安装准入分别管理。

目前支持官方稳定版 `0.14.0`、`0.15.0`、`0.16.0`、`0.17.0`、`0.17.1`、`0.17.2`、`0.17.5`、`0.17.6`、`0.17.7` 的已固定 Windows x64 per-user NSIS 包。每个目标都绑定发布者签名、官方资产身份、安装器 SHA256/大小及全部目标文件的测量清单；新版本或被替换的同名资产不能仅凭版本号自动加入。未知包装边界或未经审核的 payload 会显示对应拒绝原因。扩展官方包的信任策略须经过独立审核，不接受任意 URL 安装。

准备预约先返回不透明事务 ID，以便在下载期间取消。重复点击不会发起第二个准备。导航、失活或重新挂载会使旧选择失效，并通过原文档取消已知准备。取消未确认时，不显示成功或准备另一个安装包；文档已撤销时提示重新打开 CC Desk。网络、存储、签名和元数据错误只显示本地化安全提示；后台原始诊断、路径和凭据不进入界面。

## 数据与返回边界

这些历史版本没有已审核的共享数据兼容性规则，因此“保留当前数据”不可用。切换使用全新 Desk 设置，并先保存当前完整本地安装及匹配的 Desk 数据环境作为返回点。安装包准备步骤自身尚未创建返回点、快照或版本切换事务。

Claude/Codex 历史、凭据、配置和项目文件仍然共享，且不会回滚。旧应用功能可能修改共享 CLI 设置，全新 Desk 设置不是旧二进制的沙箱。源应用必须是可唯一核验的当前用户 NSIS 安装，并在未提权且不属于任何外部 Job 的进程中运行；活动、准备中或所有权未知的 CLI 会话阻止切换。管理器重新核验这些条件后才进行实际安装和返回。

## 命令与验证

普通窗口通过 `list_history`、`select_history`、`begin_prepare_history`、`prepare_history`、`cancel_prepare_history`、`inspect_switch`、`begin_switch` 完成目录、准备、只读准入检查和明确确认。请求使用原 NativeRuntime 文档桥；先验证文档，再解码至多 1 KiB 的严格 raw JSON，并在阻塞 IO 后重新检查同一个 binding、WebView 与文档凭证。准备服务保留原调用者及私有目录祖先句柄，不向另一个文档转移 token。确认只发送准备身份及 `fresh-settings` 模式；版本、摘要、路径和进程身份由后端持有。

Windows 准备存储在后端解析的 LocalAppData 下创建具有当前用户保护 ACL 的私有目录，从已固定的目录句柄派生能力。存储/平台条件不支持时关闭准备；该能力不构成安装范围或管理器准入证明。

前端覆盖真实 UpdateSection → store → API → 文档桥组合、Rust 准备 DTO fixture、不可用列表、分页、取消/迟到响应、重挂载和文档失效。独立视觉场景使用合成内存传输并禁止真实宿主/网络调用；它生成供人工检查的未批准截图，不修改现有截图基线。Rust/Windows 实际目录能力、编译与命令边界测试仍需 Windows CI；DOM 测试不代表像素或真实安装验收。

## 原生编排的源码状态与验收边界

Windows 正常路径的源码已经连接：专用线程完成当前安装和上下文保存，创建全新 Desk/WebView 状态，启动已验证安装器，核对实际安装字节，启动历史应用，并单独接受用户确认。只有原历史进程及其实际私有 job 全部终止后才可请求返回。返回先保留后续上下文与安装状态，再恢复原始匹配上下文、完整应用、注册及快捷方式；所有实际读回一致后才发布并读回终态 marker。

失败保留原生所有权。源上下文转移、后续应用备份准备和最终恢复读回均在检查完成后才交出 owner。进程启动后的日志、原生观察或管理器命令通道失败，会让专用线程保留原进程、job、回执及租约并报告需要恢复；不会把失败当作终止或自动重放。128 MiB 的真实最小中止保留空间只是一项有界余量，不保证全部恢复所需容量。

生产能力判定开放上述已审核目标的正常编排入口；源码连接和前端契约测试仍不是实际 Windows 往返验收证据。源码已连接受限的重开返回路径：原管理器必须先取得原受管进程的真实终态及实际私有 job 为空的证明，关闭历史启动能力，并持久化完整、尚未领取的返回检查点。重新打开保留的管理器后，必须重新取得并核验实际恢复对象及排他所有权；用户再次确认后，才能唯一领取检查点并执行返回。重开不能确认历史启动；尚未封存、领取后中断、Unknown 或证据缺失/损坏的状态只读拒绝重放。已完成状态也须核验实际恢复对象与回执后才显示完成。不能用序列化标志、PID 消失或缺失 job 名称补造封存前的进程证明。

正常路径仍需准确最终源码的 Windows 编译、测试、严格检查，以及真正独立未提权进程中的安装/启动/返回验收。用户已授权必要时使用本机，但被外部 Job 包含的本机或 GitHub 托管 runner 仍不具备该测试资格；不得使用 breakaway 或特殊宿主链规避限制。独立只读 run `37874928688` 观察到 `windows-2022` 与 `windows-2025` 的普通父、子进程均属于 Job；诊断任务成功只表示观察完成，不表示原生验收通过。注册描述符和文件变更检测保持精确比较；文件恢复读回采用下述窄范围契约，诊断保留原始描述符的有界差异。


## 文件安全描述符恢复读回

真实 Windows run `37070989995` / job `111050123104` 的 `HistorySecurity_ReadbackProbe_001` 复现：`SetSecurityInfo` 后，继承描述符控制字从 `0x8004` 变为 `0x8404`，保护描述符从 `0x9004` 变为 `0x9404`；总长度、四个相对偏移、owner、group、DACL 与 SACL 均相同。差异只有系统设置的 `SE_DACL_AUTO_INHERITED` (`0x0400`)。Microsoft 的 [自动继承规则](https://learn.microsoft.com/en-us/windows/win32/secauthz/automatic-propagation-of-inheritable-aces) 将该位定义为转入当前继承模型的记录；[SetSecurityInfo](https://learn.microsoft.com/en-us/windows/win32/api/aclapi/nf-aclapi-setsecurityinfo) 负责该转换，DACL 保护仍由 `SE_DACL_PROTECTED` (`0x1000`) 决定。

恢复比较接受原始字节完全相同，或仅原始 `0x0400` 未设置、实际已设置的单向变化。清除该位、其他控制位变化、owner/group SID 变化、DACL/SACL 有无或 NULL 状态、ACE 内容/顺序/继承标志变化、相对偏移或长度变化均不能被该例外接受。DOS 属性仍完全一致。应用点仅限文件设置器的读回、完整安装的权限/属性与最终逻辑恢复验证，以及快捷方式恢复后的验证。原始捕获、序列化、摘要、普通 `PermissionRecord`/`ShortcutState` 相等比较、写入前与句柄转换后的稳定性检查不变。当前实际捕获/恢复范围仍是 owner/group/DACL；此修正不增加 SACL/audit 权限能力。

继续使用固定目标句柄上的 `SetSecurityInfo` 和既有所有权/布局/边界检查，不切换至基于路径的旧 `SetFileSecurityW`。`SetSecurityDescriptorControl` 只改内存描述符，`SetSecurityInfo` 的参数不能要求清除该系统位。已核对 pinned `windows 0.61.3` 的 `NtSetSecurityObject` 声明与 Microsoft 用户态说明，但未验证其完整继承行为，不将底层 API 替换作为恢复捷径。

回归包括真实继承/保护文件的生产设置器读回、完整 owner/group/DACL/SACL 描述符中除允许位外逐位变化的拒绝、清除允许位的拒绝、普通相等/摘要仍保留差异，以及完整安装最终恢复与快捷方式内容/属性检查。修正后的真实 Windows 编译和测试仍待准确源码验证；此源码说明不是成功验收证据。

### 管理器仍存活时的失败恢复

源码现在为同一管理器持有的失败状态连接了显式“返回上一版本”操作。尚未启动安装器时，必须重新验证原始源进程终态、原目录/文件对象与未启动凭证：可保留实际未完成的私有副本并反向恢复已确认的源移动；若已经封存源环境，则先保留未创建、部分创建或完整的新环境，再恢复匹配的原环境。中断的纯保存状态记录只可根据实际仍被持有的完整原对象重新读取确认，不能冒充此前已经记录了封存阶段。

安装器非零退出或目标检查失败时，返回要求实际安装器终态与空的私有 job，以及在历史进程创建意图之前尚未消费的启动凭证。若受控子进程已创建、仍处于最初的挂起状态且从未尝试开始运行，用户的同一次明确返回请求可以清理该未启动尝试；之后仍须实际取得终态和空 job。任何开始运行调用（无论失败、结果未知或成功）都会永久关闭这条清理路径，不会终止已运行的历史应用或用户 CLI。

未知源映像移动/逆向移动、损坏的日志尾部、丢失或替换的原生对象、发生变化的源内容、无法验证的实际私有副本，以及无法取得真实进程/job 终态的情况仍会保留状态并阻止恢复。这些拒绝状态在重新打开管理器后仍仅提供只读检查；不能使用前述完整且未领取检查点的返回路径。正常入口可用不扩大这项恢复权限；已有原生回归结果不替代真实版本往返验收。


## 历史面板反馈与管理器截图证据

切换回执丢失或持有准备事务期间状态检查失败时，未识别错误的横幅提示与当前所有权一致：结果未知则先刷新状态，已交接则检查管理器所有权，不使用目录读取的通用重试提示。已识别的安全诊断及目录读取重试提示保持独立；旧检查的成功或失败均不能覆盖新的切换状态，也不能重放操作。

`tests/components/historicalSwitch.test.ts` 经真实面板、store 和文档客户端覆盖中英文未知回执、失败后的只读检查、已签发身份、迟到检查的成功/失败，以及目录读取仍可重试的边界。

清理检查返回不提供取消权限的有效动作子集或已签发身份时，保存的通用准备错误也必须按发布时的 `unknown` / `handoff-issued` 状态显示；后续成功检查再次发布该错误时应用同一规则。只转换 `historyErrorUnavailable`，保留已识别诊断和原准备失败记录，明确取消完成与目录读取仍使用原提示。中英文回归经真实面板、文档客户端和严格解析器覆盖这些合法回执及零重放。这是前端契约回归，不是当前 Rust 普通用户流程的复现声明：当前 Rust 通常为失败、运行中或过期准备提供取消；无已签发身份且未取消的准备，只在 Ready 且切换准入进行中不提供取消权限。已签发身份则须经过切换预约。

管理器视觉场景在 `installed-unconfirmed` 和 `recovery-required` 阶段，分别将真实 `.manager-handoff` 提示滚入可视区并检查完整可见，再保存独立的 `ownership-warning-unapproved` 截图。此捕获与断言已加入四种窗口/语言/缩放组合，用于避免仅拍摄上方共享数据段落而漏掉“关闭窗口不会取消切换”的说明。本次本地执行在浏览器启动阶段受阻：固定 Playwright Chromium 缺失，系统 Chromium 的 socket 创建被环境拒绝；该本地尝试未执行到页面断言或生成截图，CI 捕获与像素检查证据另行记录。生成后的新增截图仍需单独批准；合成 Chromium 证据不代表真实 Windows、原生安装/返回验收或基线批准。

独立所有权提示截图改为将真实 `.manager-content` 滚到 `scrollHeight`，利用已有底部内边距留出完整行框空间；仍要求交叉比例 `1`，不改 CSS、文字或可见性阈值。此修正仍待 CI 渲染验证，不能由 DOM 单元测试或用例收集代替。


## 普通签名历史安装：FreshSettings 与手动恢复备份

新的 `inspect_historical_install` / `begin_historical_install` 与严格往返切换共用官方目录、选择和保留的签名包，但有独立的准入及一次性交接身份。同一个准备结果签发给任一模式后，另一模式不能重解释或重放。请求只接受 `transactionId`（准备身份），不能提供版本、路径、执行参数、兼容性声明或成功回执。普通安装不要求 `REVIEWED` 安装文件库存；严格往返的库存及 Return 约束保持原样，最新版本自动更新仍只允许升级。

普通安装默认使用全新 Desk 设置。源进程确认退出后，管理器继续持有原全局安装控制租约，复用完整应用、注册、快捷方式、Desk 数据与 WebView 保存和读回验证，才封存源环境并创建 FreshSettings。事务从开始即使用固定私有 sibling 备份存储；完整数据保存在 `CCDesk-VersionBackups`，不写入旧版本所读取的全局活动切换 marker。没有完整备份、源进程仍存活、取消或准备失败，均不能交接安装器。现有外部 Job、提权、所有权、ACL、TOCTOU 和真实持久化保护继续适用。

安装器从同一次保留包及实际映像身份创建挂起进程，唯一启动尝试绑定原事务；仅此普通模式在精确交接时解除其私有 job 的关闭终止策略。界面“官方安装器已启动”只说明取得该进程的启动回执，不说明目标版本已安装成功、数据兼容或往返验收成功。未知回执保留备份与恢复证据，禁止自动重放。普通模式不提供自动 Return 或历史应用启动按钮。

管理器从最初阶段就明确显示普通安装模式，备份完成前位置为空；只有完整读回后才显示实际备份位置。需手动恢复时，先关闭安装器、Desk 和相关受管程序，保留整个显示的备份目录及事务记录；按其中匹配的原版本、安装、注册/快捷方式和 Desk/WebView 快照恢复，并验证实际读回。备份包含受保护状态与清单，不应当作可直接覆盖的通用文件夹。此路径目前没有一键手动恢复工具；不能直接把单个快照文件夹复制到当前数据目录。若无法核验匹配的原环境，应保留备份并寻求恢复协助，不删除记录或再次运行未知交接。CLI 外部会话、`CODEX_HOME`、`CLAUDE_CONFIG_DIR` 和项目内容不纳入恢复，也不由该流程改写。

当前要求原全局恢复存储为干净状态，仅有控制锁/生命周期锁允许存在。实际未结束事务仍持有恢复责任；已结束的可恢复记录也不能直接丢弃，因为旧版本启动读取的 marker 仍绑定原源 bundle。两者均以 `HISTORY_ORDINARY_EXISTING_RECOVERY` 明确拒绝，保留原证据。这是已有恢复记录的运行时前提，而不是正式版本永久禁用：后续可在用户明确确认后研究完整保留/迁移已结束记录，必须证明旧版本启动与人工恢复仍可定位，不能静默删除、伪造终态或绕过未结束所有权。

签名向量、状态机、页面和 manager 契约测试仅证明对应源码边界。真正普通安装仍需要准确最终源码的 Windows 编译/测试及独立未提权、Job-free 宿主实测；标准 GitHub runner 的外部 Job 限制不能用 breakaway 绕过。旧有 18 个外部 Job 专项未验证范围不得扩大或冒充通过。
