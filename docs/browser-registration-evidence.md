# Browser registration evidence

## Boundary and selected approach

The existing native `BrowserProfile::enrolled` accepts independently approved policy; it does not authenticate a person. The browser authority/store provide custody and revocation, not identity. This slice adds a native two-stage evidence verifier and an explicitly invoked browser producer. It creates no new trust root, default enrollment action, network route, storage action or grant.

The native caller independently supplies the exact origin/RP, user handle, original owner context binding, and separately selected TLS/grant/relay public keys. A fresh native nonce binds these fields into one request. The attempt owns its original cancellation token and bounded monotonic deadline; consuming Rust states prevent replay between stages. Existing private handles first prove possession of the expected public keys. The browser then requests ES256 WebAuthn creation with `attestation: none`. Native verification strictly parses the original CBOR attestation/authenticator data and COSE key, origin/challenge, UP/UV and explicit backup policy. None attestation is not authenticator provenance or credential-key possession.

Only after native creation verification does the next state issue a domain-separated assertion challenge bound to the exact accepted creation transcript, credential ID and key. The original credential must satisfy a subsequent signed WebAuthn assertion. The result is explicitly **unapproved evidence**, never a `BrowserProfile`, `GrantGate`, supplier, persisted record or authenticated human identity. The subsequent [native registration approval gate](native-registration-approval.md) holds this original value, compares its exact owner and Host-consumed identities, and requires a separate native Yes before installing one frozen Host configuration. There is still no public registration command, authenticated bootstrap channel, account identity authority or durable trust installation.

Alternatives rejected: accepting `fmt=none` as possession; using the browser candidate as trusted input; auto-installing a verified response; and treating a local confirmation dialog or mutable JSON flag as an identity authority. A hardware-attestation trust database is outside this minimal scope.

## Implementation plan

1. Add native single-use `BrowserRegistrationAttempt` and possession-pending state under the existing experimental feature, with fixture-only Rust tests. Test accepted synthetic registration and reject changed context/challenges/keys, malformed or duplicate CBOR fields, unsupported algorithms/extensions/attestation, missing UV, backup-policy violations, cancellation and the original deadline.
2. Add explicit browser create and assertion producers using existing non-exportable key handles, exact controlled origin, owned original signal/deadline and bounded native response types. Never race original platform promises against an artificial completion. Test synthetic API responses only.
3. Connect actual Edge producer output to the original compiled Rust two-stage verifier using a TEST_ONLY stdin/stdout oracle. Prove success yields only unapproved evidence and adversarial responses never yield it. No OS authenticator or real credential operation is invoked.
4. Run the affected native security suite, browser acceptance, strict producer typecheck, existing remote Node tests and independent review; locally commit only this slice.

## Real operation permission

An actual registration creates a persistent authenticator credential. It requires explicit authorization for the actual HTTPS origin/RP, account/user handle, authenticator and intended later use. Existing TLS/grant/relay handle use and final durable installation need their corresponding authorization. This implementation and its fixed public TEST_ONLY fixtures do not perform any of these real actions. Native Host approval, real WebView/platform qualification and deployment remain separate.

Verification follows [WebAuthn Level 3 registration and assertion verification](https://www.w3.org/TR/webauthn-3/). This minimal profile accepts only `none`, ES256/P-256, no extensions, and top-level same-origin ceremonies. It makes no hardware, attestation provenance, backup-recovery or human identity claim.

The output's `requestedUserHandle` is the independent owner's requested association. A returned assertion userHandle may be null; when present it must match, but is not an authenticated identity claim. Credential uniqueness and account association remain the final trusted owner's responsibility. Serialized evidence can be copied; it is not an authorization token or retirement receipt. The held native evidence object checks the original cancellation/deadline before publishing its description.

## Implemented interfaces and validation

- `remote/crates/security/src/browser_registration.rs`: native-only experimental `BrowserRegistrationAttempt::new`, `request`, consuming `verify_create`, consuming `BrowserRegistrationPossession::verify_assertion`, live `UnapprovedBrowserRegistration::description` and `matches_host_candidate`. The backend-only native registration owner imports it; no product registration command or transport exposes it.
- `remote/ui-terminal/src/browserRegistration.ts`: `createBrowserRegistrationProducer(origin, originalSignal, originalDeadline)` returns single-use `create`, `confirm`, `close` and `waitClosed`. Caller code must independently authenticate the native requests. The original deadline actively aborts the owned signal, including while idle between phases; original platform promises are retained until actual settlement.
- Internal native regressions are under `remote/crates/security/tests/support/browser_registration.rs`, outside Cargo's standalone integration discovery. The ignored `Registration_BrowserOracle_900` is invoked explicitly by actual Edge tests, not treated as covered by the ordinary native suite.
- `tests/remote-browser/browser-registration.spec.ts` replaces `credentials.create/get` with fixed published scalar fixtures before invoking the production producer. It exchanges real output bytes with the original compiled Rust verifier over a TEST_ONLY process pipe. It never opens an OS authenticator prompt.
