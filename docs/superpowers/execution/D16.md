## Implemented contract

### Per-run ordered user intent queue

- Each queue is bound to one immutable `runId` + `generation`.
- Every user action receives a canonical decimal-u64 `inputSeq` synchronously.
  Async paste/clipboard work reserves the sequence before its promise resolves.
- A pending earlier user action blocks later user text, Enter and paste intents.
  Later actions cannot overtake it merely because their bytes are ready first.
- Equal byte payloads remain distinct actions. No content hash, time window or
  payload equality is used to deduplicate separate user intents.
- Async producer failure pauses the queue at the failed sequence. A later Enter
  does not escape and submit an older terminal draft.
- An empty/zero-byte paste is treated as a failed barrier rather than a successful
  no-op, so a later Enter cannot be released merely because clipboard text was empty.
- Recovery is explicit. `continue` discards the failed action and keeps later
  queued actions; `cancel` clears the run queue. A stale target or mode epoch
  cannot be silently rebased by `continue`.
- Immediately before the actual dispatch critical section writes, the queue
  rechecks current run ID, generation and mode epoch. A restart/mode change while
  waiting for another send therefore cannot redirect old bytes into a new run.
- Single action bytes are capped at 8 MiB and total queued payload for one run at
  16 MiB by default. Over-budget input is rejected before dispatch; no truncation
  or rewrite occurs. Tests can use lower explicit limits to prove the accounting.
- Stored input uses defensive byte copies so later caller mutation cannot alter a
  queued action.

### Source routing

- Explicit user text is UTF-8 encoded and may enter the ordered user queue.
- xterm `onBinary` data preserves 0–255 byte semantics and uses a protocol-bypass
  lane rather than being UTF-8 re-encoded.
- xterm `onData` is deliberately classified as ambiguous/legacy-direct in this
  stage. The installed xterm 5.5.0 public callback supplies data but not reliable
  user-vs-terminal-response provenance, so D16 never infers protocol traffic from
  bytes such as DSR-looking `ESC[...n` sequences.
- Protocol-bypass traffic may cross an unresolved clipboard reservation because
  no user write has begun. It shares the dispatch gate once a user frame is
  actively sending, so it cannot interleave inside that frame.
- Protocol target identity is revalidated after waiting for the dispatch gate;
  stale protocol output is rejected with `STALE_INPUT_TARGET`.

The existing legacy `XTermTerminal.vue` path is not migrated here. That prevents
D16 from pretending an ambiguous `onData` event has provenance it does not have.
D17 supplies the native byte writer and D18 later supplies the single UI
arbitration path.

## Covered D16 cases

The 12 D16 unit cases cover:

1. pending paste followed immediately by Enter cannot reorder;
2. clipboard/producer failure pauses later user intents until explicit recovery;
3. two equal paste bodies retain distinct input sequences;
4. mode epoch change pauses rather than retargeting old input;
5. protocol bypass crosses an unresolved clipboard barrier but not an active send;
6. DSR-looking `onData` text is never guessed to be protocol;
7. `onBinary` preserves raw 0–255 bytes;
8. explicit user text uses UTF-8 and the user queue;
9. generation change rejects the old run queue;
10. action/run budgets reject without truncation/reordering;
11. target identity is rechecked after waiting for the dispatch gate;
12. empty paste is a failed barrier and cannot release a queued Enter.

These are A-layer host/ordering tests. They do not mark the later real CLI
NATIVE-41 through NATIVE-45 certification cases as globally PASS.

## Limits and next task

- D16 does not claim that current legacy xterm `onData` has trustworthy source
  provenance. Ambiguous traffic stays outside the new ordered user queue rather
  than being heuristically classified.
- No production native input RPC/writer is added by D16. D17 must implement
  bounded byte staging, 64 KiB upload chunks, exact owner/run/inputSeq handling,
  exclusive host writes and explicit host-write receipts.
- `hostWritten` will mean only that Desk completed the host write. It must not be
  described as CLI submission/consumption.
- Partial or uncertain write failure, no-replay policy and subsequent user-input
  freeze belong to D17.
- DOM paste, system menu paste, keyboard shortcuts, image-paste convenience and
  IME arbitration remain D18 / PR12.
- Full terminal protocol certification remains D19/D20; D16 only prevents unsafe
  source guessing in the new path.
- No real model-backed CLI workflow, installer certification, merge, tag or release
  is claimed here.
