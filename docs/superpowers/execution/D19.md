## Implemented contract

### Source-proven xterm input routing

- D19 does not classify `onData` by escape-sequence contents, regexes, printable/non-printable bytes, timing guesses or clipboard state.
- The pinned `@xterm/xterm` runtime is exactly 5.5.0 from `package-lock.json`.
- xterm 5.5 user-originated data is identified from the existing internal `coreService.onUserInput` signal that fires immediately before the corresponding public `onData`.
- Each user-input signal authorizes exactly one following `onData`; additional `onData` events remain protocol-originated.
- If the pinned runtime no longer exposes the provenance signal, binding fails closed with `XTERM_USER_INPUT_PROVENANCE_UNAVAILABLE`; there is no byte-content fallback.
- The host protocol also rejects an unbracketed `onData` source as `AMBIGUOUS_XTERM_DATA_SOURCE` and rejects simultaneously asserted user/parser provenance as `CONFLICTING_XTERM_DATA_SOURCE`.
- `onBinary` remains raw 8-bit protocol traffic and preserves byte values without UTF-8 reinterpretation.

### Shared D16 input dispatch gate

- Explicit user text enters the existing D16 ordered input intent queue with the captured `modeEpoch`.
- Parser replies and `onBinary` use the same queue's exclusive protocol dispatch gate rather than bypassing an in-flight user write.
- User writes go through the authenticated staged document bridge `cliWriteInput`.
- Protocol writes go through the authenticated document bridge `cliWriteProtocol`.
- A write is accepted only when the receipt state is `host-written` and `confirmedBytes` exactly equals the submitted byte length.
- Partial/unknown or mismatched receipts fail the active dispatch; the existing D16 queue then pauses and leaves later user input unsent instead of replaying or silently advancing it.

### Output parse and ACK ordering

- Native output is delivered through the existing D14 output transport.
- `term.write(bytes, callback)` supplies the parser-completion callback.
- The cumulative output ACK is sent through `cliAckOutput` only after that parser callback executes.
- Disposing the binding removes xterm subscriptions and stops accepting new output frames.
- Async route failures are retained until `drainInput()`; they are not converted into detached unhandled rejections or silently lost.

### Production composition

The production composition root `createDeskNativeTerminalBinding` connects the xterm-facing binding only to the authenticated document bridge APIs already established by D11/D14/D17:

- `cliWriteInput`
- `cliWriteProtocol`
- `cliAckOutput`

No test-only transport, direct PTY shortcut, prompt parser or content-based terminal classifier is exposed as a production fallback.

## Continuation boundary

D19 proves the generic terminal-host routing contract on the corrected D18 lineage. It does **not** certify that a particular installed Claude Code or Codex CLI version behaves identically inside CC Desk and a system terminal.

D20 must therefore use isolated roots, temporary projects and authorized test accounts to produce real CLI evidence for both products. The evidence must bind the exact CLI binary/version/hash and target identity to the same run/session/turn where available; preserve the raw `UserPromptSubmit` envelope; compare host payload against the versioned transform; and record unavailable/unverifiable combinations as `BLOCKED` rather than substituting screen parsing, model repetition or writer success.

Current official product documentation confirms that both Claude Code and Codex expose a `UserPromptSubmit` lifecycle event, but online documentation is not evidence for the installed binary. D20 records the actual target version/schema before allowing a PASS.

No merge, tag or release is part of D19.
