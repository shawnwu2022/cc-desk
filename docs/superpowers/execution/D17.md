## Implemented contract

### Two-stage bounded upload

- Native user input is staged before any PTY write. The wire path is
  `begin -> chunk* -> commit`, with explicit `abort` for a staged action.
- A single action is capped at 8 MiB, upload chunks at 64 KiB, and per-run staged
  payload accounting at 16 MiB. Oversize, incomplete, out-of-order and conflicting
  chunks are rejected before the writer callback is entered.
- Staging identity is owner-scoped and includes document instance, window label,
  WebView epoch, run ID and generation. User actions are additionally keyed by
  canonical decimal-u64 `inputSeq`.
- Equal payload bytes are not a deduplication key. Sequence identity remains the
  authority; exact duplicate chunks are idempotent while conflicting overlaps are
  rejected.
- Abort is a zero-write operation. A finalized sequence cannot be silently reopened
  as a new action.

### Exclusive writer and receipts

- `cli_input_commit` first revalidates the authenticated run, then the existing
  `RunAccess::with_writer` path revalidates ownership again after waiting for the
  per-PTY writer mutex and immediately before the host write.
- The complete staged frame is passed through one exclusive writer section. Wire
  chunking is not exposed as PTY write interleaving.
- `write_host_frame` loops on `Write::write`, records only confirmed returned byte
  counts, and flushes before reporting `host-written`.
- `host-written` means the Desk host write completed. It is never described as
  proof that Claude/Codex parsed, submitted or consumed the bytes.
- A write error, zero-progress write, invalid writer count, flush failure or writer
  panic becomes `partial-or-unknown`. The receipt may expose a confirmed prefix,
  but never invents a CLI-consumed count.
- Once a user commit becomes `partial-or-unknown`, later user input for that run is
  frozen. The failed payload is not replayed and no Enter or process restart is
  synthesized.
- A same-sequence duplicate of the most recently finalized commit returns its stored
  receipt without re-entering the writer.
- Safe failures before the host write begins restore the staged frame rather than
  fabricating a partial write.

### Protocol and stop isolation

- `cli_input_protocol` uses an authenticated direct byte request and the same
  per-PTY writer mutex, so protocol bytes cannot interleave inside an active user
  frame.
- The protocol request is bounded to 64 KiB and preserves raw byte values.
- Explicit Stop remains process control, not terminal input. The owned-PTY
  `D11_Owned_RootControlDoesNotWaitForWriterOrWaiter_04` test already proves root
  termination does not wait behind the writer mutex or waiter handle, so D17 does
  not weaken that boundary.

### Frontend transport API

- `cliWriteInput` slices a complete `Uint8Array` into at most 64 KiB wire chunks,
  sends one begin and one commit, and does not automatically retry a failed commit.
- A staging failure performs only a best-effort abort and rethrows the original
  failure; it does not continue to commit or replay the payload.
- A `partial-or-unknown` commit receipt is returned to the caller unchanged.
- `cliWriteProtocol` accepts raw protocol bytes only through the document-authorized
  bridge; neither input API falls back to an unguarded global invoke path.

## TDD evidence

### Behavioral RED

Commit `dea5904a12d46c1b2702460338ec2e619ccf4088` registered the D17 tests while
`terminal_input.rs` still contained the explicit not-ready scaffold. CI #332 /
run `36095282806` failed the Rust job exactly as intended:

- the existing library baseline remained 661 passed / 20 ignored;
- failures returned `NATIVE_INPUT_NOT_READY` or the corresponding scaffold receipt
  mismatch;
- the frontend job remained green.

This is the product RED. The assertions were not weakened to make the implementation
pass.

### Failure-path hardening

After the initial implementation, additional tests locked down:

- writer panic -> `partial-or-unknown`, frozen user input and no replay;
- active commit state surviving concurrent staging-state access;
- exact production source compiling and linting on Ubuntu, Windows and macOS;
- frontend two-stage upload, abort-on-staging-failure, no automatic partial replay,
  protocol byte preservation and document-authority failure;
- NATIVE-42 as one combined case: a payload larger than one 64 KiB upload chunk,
  a writer failure after a confirmed prefix, frozen later input and a duplicate
  commit that does not call the writer again.

The NATIVE-42 coverage commit is
`5e1c6851d08463e238c3055f1cce08f97cdfd3dd`.

## Limits and next task

- D17 does not migrate the legacy `XTermTerminal.vue` input path. D18 owns the
  single DOM/system-menu/keyboard paste arbitration and IME policy.
- D17 does not infer terminal protocol responses from arbitrary `onData` bytes.
  Trustworthy source routing remains the D16 contract; D18/D19 must connect it to
  the adopted terminal path without heuristics.
- NATIVE-42's source-level writer-fault semantics are now directly regression-tested,
  but this ledger does not relabel unrelated real CLI / WebView / installer cases
  as certified. Target-matrix promotion remains evidence-gated.
- Staging/writer success is host-side evidence only; real Claude/Codex parsing,
  terminal protocol behavior and packaged target certification remain later tasks.
- No dependency/version change, merge, tag or release is part of D17.
