## First-increment evidence (historical)

The first increment at `e0cad1aa` established source-aware cache partitions and removes stale config-panel publication. At that checkpoint D12 was **not complete**: the authenticated `native_get_scope` / `native_list_resources` commands, owner/profile/run revision checks and all resource readers still need migration before the new dual-CLI UI may use them. A cache partition is not a filesystem permission or a SourceScope capability.

The D11 production `NATIVE_RUNTIME_NOT_READY` gate stays unchanged. Do not interpret passing cache tests as real CLI, live WebView, all-platform or packaged-installation certification. No native history/config deletion, version/lockfile update, main merge or release belongs to this increment.

## Remaining-work implementation

The continuation registers **production** `native_get_scope` and `native_list_resources` commands in
`commands.rs` and `lib.rs`. Both use D11's actual `DocumentBinding::admit_native` before decoding
bounded raw requests. A frontend root path, caller label, or scope ID alone cannot grant access.
`NativeRuntime` calls `ProjectionService` on a blocking worker and rechecks the document before
returning. The D11 CLI-start runtime gate is not opened by these read-only commands.

### Backend authority and lifetime

`ProjectionService` resolves a profile revision or an authorized `(runId,generation)`; it never
accepts a native root path in its wire DTO. `ScopeRegistry` retains directory capabilities together
with backend instance/window/document epoch, CLI, profile revision, root identity, scope identity
epoch, and target/basis. Each source-reference field is checked against that exact registration.
Registration/reuse and every catalog read recheck authority; a profile scope compares the current
stored profile (not only its revision) and root-affecting host environment. A run scope reads its
frozen launch snapshot and checks current `RunAccess`; changing/deleting the profile does not
rewrite a running process's frozen environment. Old generation/document references are rejected.

The basis is explicit: **configured-profile** or **launch-environment**, never a claim about all
configuration mutations inside a running CLI. Shell/shim/raw launches and unknown extra/default
argument semantics return `SCOPE_UNKNOWN`, not a guessed default root. A no-extra-args new native
launch may grant its frozen requested cwd; resume/picker scopes do not infer an effective project.
Explicitly registered project IDs are resolved by the backend. Transcript `cwd` values are only
filter data, never an instruction to open a directory. Verified selected/canonical project spellings
are checked against the held physical directory identity; arbitrary persisted aliases are not trusted.

### Filesystem reads and budgets

`Root` uses pinned `cap-std` directory handles for descendant enumeration/opening; it does not use
ambient `path.join(...) + fs::read`. The ambient selected path is used only to admit/recheck the
root's identity. Unsupported paths, symlink escapes, device/FIFO entries, invalid UTF-8/NUL,
root replacement, file mutation, unsupported schemas and read failures fail closed. Windows may
prevent replacing a held directory; tests cover either that denial with unchanged original reads,
or successful replacement followed by explicit source invalidation. This is read confinement,
not an OS sandbox for the independently running CLI. Hard links and mutable file contents are
not represented as an atomic filesystem snapshot.

Initial limits: 64 registered scopes, 2 simultaneous catalog scans, 2 MiB per file, 16 MiB total
input bytes, 4096 visited entries, cooperative 5-second checkpoints, 200 response items/page and
2 MiB encoded response. OS filesystem calls are not forcibly interruptible. Exceeding a scan/schema
limit returns **unavailable**, not a partial list marked ready; pagination uses `hasMore` explicitly.
History titles/message/document excerpts expose truncation flags. Metadata descriptions are summaries.
No source data is written or deleted. There is no process spawn, credential expansion, or plugin
activation in a catalog read. New authenticated catalogs use bounded fresh reads rather than a
cross-request native-content cache. Existing v2 legacy cache partitions remain separate.

| Legacy concern | Scoped replacement | Boundary |

| Message details/search | Same confined transcript reader, `messages`/`search` kinds | Target session ID/query stays within its authorized source; transcript cwd never grants project reads. |
| Config/basic settings | `catalog/metadata.rs`, `config` kind | Small non-secret scalar allowlist; no full config/environment/credential return. |

| Skills/legacy commands | Root/project skills plus bounded Claude command/plugin markdown | Fixed source roots; no plugin CLI invocation or arbitrary install-path fallback. |
| Agents | Claude markdown directories; declared Codex agent table observations | Description/model observations are not proof of active agents. |
| Plugins | Claude installed/enabled records; declared Codex plugin config observations | Unknown installation scope/schema unavailable; installPath must be within the retained native root. |
| Instructions | Fixed `CLAUDE.md`/`AGENTS.md` under granted roots/projects | No arbitrary ancestor walk or transcript-directed file read. |
| Native deletion/archive mutation | **No command/action in the new projection API** | Workspace remove/hide changes Desk registration only. |

Default Claude's sibling `.claude.json` is a separately granted fixed-file source. A custom root
does not silently acquire the unrelated host home. Config metadata is an on-disk observation, not
an effective config precedence/activation evaluator. Root/project settings and plugin manifests
outside the granted roots are not followed. The markdown frontmatter reader supports only scalar
name/description/model fields; unsupported layouts must not be described as a complete effective
CLI configuration. Codex reads supported JSONL rollout records and TOML declarations, **not a
history database**; mixed duplicate user-event/response representations must agree before one
representation is used. Equal successive user prompts retain multiplicity.

### Frontend and workspace integration

`src/api/nativeProjection.ts` validates exact DTO fields, canonical u64 strings, source/instance/
profile/run/basis identity, request epoch, kind-specific item fields, encoded size, and unavailable
semantics. It copies request values before awaiting; caller mutation cannot alter an in-flight
request. No document bridge means unavailable, never a legacy `invoke` fallback.

`nativeProjection` store clears old visible data at selection time and uses non-reused request
epochs plus request ownership to reject late success/error/finally. `config.loadNativeResources`
exposes that authenticated path separately from the old Claude panel. Workspace enrichment is
owned by the current home/profile selection; older list replies cannot restart old enrichment.
Concurrent native enrichment is batched by two and never mutates registered-project membership.

**D22-D24 boundary:** this delivers the source-aware production service/API/store entry points.
Existing legacy Claude-only Vue UI callers are retained under the plan's explicit legacy allowance;
the later dual-CLI Tab/UI tasks adopt the new entry points. This change does not claim the dual-CLI
UI is finished or that old legacy APIs have acquired the new authorization contract. New Codex/
custom-root callers must not invoke them.

### Verification and release boundary

Core tests compile the actual source modules through `tests/native-cli/scope-core` using a committed
lockfile, with Linux/Windows/macOS CI. They are not a mock filesystem or a replacement reader.
Production-service tests exercise the actual workspace repository and process-backed run snapshot.
The Windows live fixture uses Wry/WebView2 and the formal command handlers to check independent
roots, missing proof, raw-body enforcement, path/reference forgery, body budget, profile revocation,
peer rejection and reload rejection. It uses only disposable synthetic fixtures, no user CLI account.
Exact final head, CI run, platform results and any failures are recorded in PR #20 after execution;
new tests or a passing headless suite alone do not establish native integration success.

Local RED/GREEN evidence includes parser/request stubs, cross-root authorization/revocation,
delayed request ownership, old-home selection, decoded NUL, mixed Codex records, unsupported scan
depth and unknown plugin scope. Production build exposed unsupported BigInt literal syntax; it was
fixed without raising the existing build target. Full-application Windows validation is a separate
gate from the headless reader tests. Existing real CLI/account-dependent acceptance remains D20;
installation/signing certification remains later release work. Ignored cases are not counted as passes.

Review is author self-review (no independent reviewer/subagent was available). No main merge, tag,
release, native config/history mutation or CLI-start gate removal is included. Three new direct
capability/parser requirements are pinned (`cap-std`, already-transitive `libc`/`toml`); lock changes
add capability support without changing any previously locked package version. Existing dependency
audit advisories are not declared fixed by this work.
