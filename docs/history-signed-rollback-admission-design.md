# Dynamic signed historical rollback admission

Status: catalog selection/preparation is dynamic; durable installation remains blocked unless the existing exact installed-output policy admits the package. This document specifies the missing adapter, not a completed installer implementation or Windows roundtrip acceptance.

## Evidence and present boundary

`catalog.rs` now admits a historical stable release using its official repository metadata, one exact `CC.Desk_{version}_x64-setup.exe`, one matching `.sig`, uploaded state, bounded sizes, SHA-256 digests, and exact official download URL. No per-version catalog table remains. Selection is metadata-only. Existing `VerifiedPackage::finish` checks downloaded sizes/digests and Minisign under the committed publisher key, then retains and rechecks the same private package object and bytes. Neither property supplies an installed-output inventory.

`PayloadAdmission::for_selection` currently supplies that inventory from `REVIEWED`. `review_block` withholds `BeginSwitch` for unknown output inventories; `SourcePreflight::admit` calls `admit_begin` before document freeze/handoff. Later Windows source preparation binds the payload digest to the journal and checks disk capacity. The coordinator snapshots source state before installer effects, verifies installer exit and owned-job quiescence, and repeatedly compares the complete held target inventory to expected output hashes plus preserved source companions before launch and during Return. Removing the inventory gate alone would remove these checks.

Read-only inspection of the existing local official 0.18.3 package found the NSIS first header at byte 52736 (`NullsoftInst` at 52744), declared uncompressed header size 75272, and archive size 7692320. Its PE resource bytes contain ProductName `CC Desk` and ProductVersion/FileVersion `0.18.3`. These observations identify a plausible adapter input; string scanning is not a production PE resource validator. The installer stub is PE32/i386: an x64 target must be established from the embedded application executable, not the stub architecture.

No NSIS extractor is a current Rust dependency or installed executable. The installed libarchive rejected this exact package with `Unrecognized archive format`. Attempts to download the official 7-Zip Linux inspection binary returned HTTP 403, so extraction of the actual package has not been demonstrated here.

## Smallest replacement that preserves output verification

Implement an internal package-to-inventory adapter after publisher verification and before source effects. It must accept only the existing held `VerifiedPackage` (and equivalently reopen the retained verified package in the copied manager), rather than caller paths or manifests. It derives owned expected files, byte totals and policy digest from the same authenticated bytes and selected product/version. Replace the static `MeasuredPayload` reference with the owned derived inventory. Preserve existing journal binding, exact selection checks, source companion observations and `VerifiedInstalledPayload` comparisons.

A pinned NSIS-capable extraction library or packaged 7-Zip helper can decompress files and reconstruct `uninstall.exe` without running the installer. The official [7-Zip NSIS handler](https://github.com/ip7z/7zip/blob/main/CPP/7zip/Archive/Nsis/NsisHandler.cpp) implements `UninstallerPatch` and reconstructs the executable stub plus appended uninstaller data in `Extract`. [NSIS WriteUninstaller](https://nsis.sourceforge.io/Reference/WriteUninstaller) creates the uninstaller during installation; simply treating compressed file blocks as finished executables would miss that reconstruction.

The adapter needs more than an archive listing. It must establish which extraction records write to `$INSTDIR`, their exact relative destination paths, conditional or duplicate writes, directory entries, and final file attributes. Plugins and temporary WebView installer files must not become app outputs. Unsupported or ambiguous instructions, path aliases/collisions, dynamic destinations, incomplete extraction, unsupported compression and unknown attributes fail closed. Extracted executable PE resources must be structurally parsed to bind product/version and the main image's x64 architecture. Metadata product/version, archive paths and PE resources are mutually checked; none independently proves the complete output mapping.

The pinned [Tauri 2.10.1 NSIS template](../tests/fixtures/version-history-payload/tauri-2.10.1-installer.nsi) puts the main executable/resources under `$INSTDIR`, uses `File /a` for resources, and creates `uninstall.exe` with `WriteUninstaller`. This template is a useful supported layout reference, not proof that an arbitrary signed historical installer follows it. The parser must inspect the authenticated package's actual instructions. Do not introduce a per-version replacement table.

For a helper implementation, create a fresh private staging directory with existing same-user ACL/object protections and no live app/data paths. Pin the packaged helper's bytes/version/license and resolve it from protected application resources; never use ambient PATH. Hold the exact package through extraction. Bound input, header/decompressed bytes, item count, depth, per-file bytes, total bytes, CPU/time and helper output. Validate names before writing, reject traversal/reparse/hardlinks/ADS/case collisions, and capture outputs under held no-follow handles. Prefer an adapter that returns bytes/inventory through an existing private internal boundary; no new external protocol is necessary. A helper needs suspended owned-job execution, cancellation/drain and same-object evidence equivalent to the current subprocess boundaries, plus package pinning/deployment and parser security review. An in-process NSIS parser removes helper deployment but requires decompressor and instruction/string decoding, uninstaller reconstruction and supported-layout validation; the existing 7-Zip implementation spans multiple substantial C++ files. Neither is a small allowlist deletion.

Expected hashes/sizes can then be computed from authenticated reconstructed output bytes. Existing installed Windows permission/attributes and source companion assertions remain independent: exact source companions retain content, object identity, links, permissions and attributes; expected output attributes must derive from the authenticated instructions rather than guessing that every file is archive attribute 32. The held target tree must continue to reject extra, missing or changed files and recheck at launch/Return boundaries. FreshSettings isolation, sealed backups, ownership/job checks, TOCTOU, anti-replay and protected retained-package reopens stay intact.

## Why a staging installation is not the replacement

Running the installer with `/D=<temporary directory>` still executes its program, registry operations, plugins and hooks. The current [installer hooks](../src-tauri/installer.nsh) delete old CC-Box HKCU shell keys and write CC Desk shell registrations. The template also writes uninstall/product registration and shortcuts and may install WebView. A temporary destination does not isolate HKCU or process side effects. It cannot serve as a pre-effect inventory probe without an isolated Windows execution environment and separate ownership/recovery design, which is outside this bounded source change.

## Verification and remaining work

The synthetic v0.18.1–0.18.3 catalog test was observed failing first with `PackagingBoundaryUnknown`, then the actual catalog/policy/types modules passed all 16 catalog tests in `/tmp/ccdesk-history-catalog-core` using Rust 1.98.1 and cached dependencies offline. Nine Node payload/signature fixture policy tests passed. Fixtures are synthetic metadata for admission behavior; old signed assets and measurements were not changed. A Rust regression also explicitly asserts that newly selectable metadata still returns `HISTORY_PAYLOAD_UNVERIFIED` and does not enable roundtrip/BeginSwitch; its native suite needs the repository Rust test environment.

The next implementation prerequisite is choosing and supplying the authenticated NSIS extraction adapter and validating its complete mapping against clean and companion-seeded Windows installations, including reconstructed uninstaller equality. Actual Windows installation, historical launch, complete snapshot/restore roundtrip, and helper deployment have not been verified by these tests. Catalog visibility, verified download, installed-output admission and data compatibility remain separate facts.
